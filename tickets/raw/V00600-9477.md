## Description (Jira raw)

### 1. Background

Currently, push notifications are primarily triggered based on Firestore `onSnapshot` change detection.

However:

* The connection is not always consistent.
* `onSnapshot` depends on real-time listeners, which may be delayed or interrupted.
* The current approach lacks sufficient error tolerance and reliability.

As a result, there is a risk of:

* Delayed push notifications
* Missed notifications
* Inconsistent delivery behavior

### 2. Objective

* Improve reliability of push notification delivery
* Introduce a primary and fallback mechanism
* Prevent duplicate push notifications
* Improve observability and service health monitoring

### 3. Proposed Architecture

We will introduce a **dual-path notification system**:  
<custom data-type="smartlink" data-id="id-0">https://www.figma.com/board/3MfmY8K7Qhcu2nLks9L2u0/-JP-FigJam--HOGUGU?node-id=14615-144379&t=H36Du4TlH6R9IgnH-4</custom>   

#### 3.1 Primary Path (RabbitMQ)

1. `mobile/web` writes message to Firestore
2. `booking-api` publishes event to RabbitMQ (`chat.newMessage`)
3. `notification-service` consumes the event
4. Apply Redis-based deduplication
5. Send push notification via OneSignal
6. Update message notification status

#### 3.2 Fallback Path (Firestore onSnapshot)

* `notification-service` continues listening to Firestore changes
* Acts only as a fallback when the RabbitMQ path fails

Fallback logic:

* Triggered on `updatedTime` change
* Check message notification status
* Apply Redis deduplication
* Send push only if not already sent

### 4. Deduplication Strategy

To prevent duplicate push notifications:

#### Redis-based Deduplication

* Use a unique key per message per recipient:

    ```
    dedup_key = recipientId + messageId
    ```
* Use atomic operation:

    ```
    SET NX EX (TTL: 30–60s)
    ```
*  If key exists → skip push 
*  If key does not exist → proceed 

### 5. Notification Status Management

Each message (per recipient) will include a notification status:

* `pending` → not yet sent 
* `sent` → successfully sent 
* `failed` → attempted but failed 
* `skipped_duplicate` → prevented by dedup 

Rules:

*  Only send push when status = `pending` or `failed` 
*  Do not send when status = `sent` 

### 6. Failure Handling

*  RabbitMQ path is the primary mechanism 
*  If RabbitMQ fails (publish/consume issues), fallback will handle delivery 
*  Fallback must: 

    *  check status 
    *  respect dedup logic 
    *  avoid immediate race (optional delay - 5s or more) 
    

### 7. Monitoring & Health Check

To monitor system health, we will track:

* **Unsent count (**`pending`**)** 

    *  Indicates messages that have not triggered push 
    *  Sudden increase may indicate failure in delivery pipeline 
    

Additional recommended metrics:

*  Push send success/failure count 
*  Dedup skip count 
*  RabbitMQ publish/consume success rate 
*  Fallback trigger rate 

### 8. Expected Outcome

*  Improved reliability and fault tolerance 
*  Reduced duplicate push notifications 
*  Better observability of notification system 
*  More consistent user experience

### T003. Le Hoang Lam — 2026-05-22T13:17
<custom data-type="mention" data-id="id-0">@C079.Hung Hoang Tuan</custom> 

The reason I'm not suggesting Status Management per message is that the cons far outweigh the pros:

* **Write volume**: Every message × every recipient = 1 MongoDB write for status tracking. In active chat, this is significant — it essentially doubles storage for messages going forward (1 copy in Firebase + 1 notification record in MongoDB, both contain all message constrains required for a push metadata), adding cost. Redis keys have TTL and auto-cleanup. MongoDB storage grows rapidly and requires future effort to maintain, or it will silently slow down the system. This is particularly risky because the notification layer is hidden infrastructure, not business logic — it's not somewhere people naturally look when things begin go wrong.
* **Complexity**: Adds state machine logic, retry queues, and status transitions — roughly 50-70% more implementation effort. The status field doesn't solve any business requirement, isn't displayed anywhere, and isn't needed by any downstream feature.
* **Race condition risk**: Two paths can both read status = pending simultaneously before either writes sent — this requires atomic updates or transactions to solve correctly, adding yet more complexity.
* **Overkill for dedup**: Redis SET NX already solves 100% of the dedup concern with a single atomic operation. Adding a DB-based status check on top doesn't improve safety — **it only introduces the race condition mentioned above.**
* **Latency**: A DB read before every push adds 5-20ms per notification. It doesn't add any further dedup safety, but it does add a new failure point and dependency to the mechanism  (mongoDB connection).
* If you still concern about data for monitoring and statistics, Redis-based counters are sufficient — we can aggregate and export daily if historical data is needed, without the overhead of per-message document storage in MongoDB.

### T003. Le Hoang Lam — 2026-05-22T15:17
<custom data-type="mention" data-id="id-0">@C079.Hung Hoang Tuan</custom>   
  
Yes, message data is only stored in Firebase (Firestore). Our server does not store message content — it only stores a notification record in MongoDB (just metadata: recipientId, timestamp, type — no message body, no status transition logics).  
Regarding adding status fields to Firebase:  
I'd recommend against this for a few reasons:

1. Running Cost: Every Firestore write operation is billed. At **same** current traffic, adding a server-side write per notification roughly **doubles** our Firestore write cost for the notification flow.
2. Implementation Cost: As the proposal plan, coding time will be 3.5d Back-end, if adding mongoDB notification-status state machine logic and status transition, implementation time will be +2d added. If adding notification status in message on Firebase, implementaion timm will be +1.5d added. (original BE estimation is 5d, I spent 1.5d for catching up Hogugu source code and write proposal plan already)
3. Not the right store: Notification status is server infrastructure concern, not chat state. Mixing it into the same Firestore documents that clients read/write for chat adds **coupling issue** between systems.  
  The Redis-based approach keeps notification logic entirely server-side with no impact on the Firebase data model.
